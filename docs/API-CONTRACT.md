# MVP API contract (implementation reference)

Python standard library server, SQLite persistence, plain JS/CSS frontend. Local-only, no live external requests. All dates ISO 8601 UTC strings. Money is integer JPY. API errors `{error: string}` with 400/403/404/409/413/503. All mutations POST JSON and require `X-CSRF-Token` from GET state. UI must use textContent/escaped HTML for user fields.

## GET /api/state

Returns `{csrfToken, config:{mode:'mock',liveEnabled:false}, profile, sources, campaigns, plans, matches, drafts, posts, metrics, performance, campaign_performance, analysis, summary, tasks, audit, collection_settings}`.

- profile: `{name,bio,audience,niche,tone,pillars}` (pillars is string)
- sources: `[{id,text,url,author,likes,reposts,replies,impressions,author_followers,topic,posted_at,collected_at,is_mock}]`. `posted_at` ISO 8601 UTC (may be `''` for rows created before this field existed). `author_followers` integer >=0.
- collection_settings: `{keywords:[string],genre,watched_accounts:[string],period_days}`. Singleton, defaults `{keywords:[],genre:'',watched_accounts:[],period_days:7}`. Consumed by the source provider (see Providers below), not sent to any external API.
- campaigns: `[{id,name,network,url,affiliate_url,category,target,appeal_points,reward_conditions,prohibited_expressions:[string],reward_yen,status,notes,updated_at,is_mock}]`; status candidate/applied/approved/rejected/paused. `category` doubles as the "genre" dimension used for matching. `prohibited_expressions` are checked verbatim (substring) against draft text in `/api/drafts/check`. Seed campaigns clearly fictional. Manual entries not mock.
- plans (投稿企画): `[{id,campaign_id,source_id,target,theme,hook,structure,appeal,cta,match_score,created_at,is_mock}]`. `source_id`/`match_score` nullable (plan created without a reference post). `appeal` is a comma-joined list of appeal category keys (may be `''`).
- matches (④案件管理のマッチ候補): `[{campaign_id,source_id,score,reasons:[string]}]`, top 5 per **approved** campaign only, sorted by `score` desc. Computed fresh on every `GET /api/state` from `CampaignMatcher` (see Matching below) — not persisted.
- drafts: `[{id,title,text,campaign_id,source_id,plan_id,status,checks,created_at,updated_at,is_mock,publish_intent_url}]`; status draft/review/approved/exported. `plan_id` nullable — set when the draft came from `/api/drafts/generate-from-plan`, cleared by `/api/drafts/save` if the draft is reassigned to a different campaign/source. `checks` null or `{passed,weighted_length,issues:[{code,severity:'error'|'warning',message}],checked_at}`. `is_mock` indicates sample-linked content. `publish_intent_url` (see Publishing via X Web Intent below) is a ready-to-open `https://x.com/intent/tweet?text=...` URL when `status` is `approved`/`exported`, else `null` — this is the only server-side gate behind the "Xで投稿" button, so an unapproved or preflight-failing draft can never get one.
- posts (⑦投稿管理 — 実際にXへ投稿した記録): `[{id,draft_id,plan_id,campaign_id,source_id,title,text,url,published_at,status,created_at,updated_at,is_mock}]`. One row per draft (`draft_id` UNIQUE — `/api/posts/publish` upserts). `status` published/stopped/removed. `plan_id`/`campaign_id`/`source_id`/`title`/`text` are **snapshotted from the draft at first publish** (not re-copied on a later correction call) so a post's displayed content — and the campaign/plan/source it traces back to — never silently changes if the draft is edited or reassigned afterward; the frontend renders `post.title`/`post.text` directly rather than looking up the live draft. Never written by this app posting to X itself — only by the human confirming after they posted manually.
- metrics (投稿ごとの成果、手入力): `[{id,post_id,impressions,likes,reposts,replies,link_clicks,conversions,revenue_yen,recorded_at}]` unique per **post** (not per draft — see `/api/metrics` below), upsert cumulative totals, not additive.
- performance (投稿ごとのCTR/CVR/Eng率/EPC/RPM, derived, not persisted): `[{post_id,draft_id,plan_id,campaign_id,source_id,campaign_name,hook,structure,appeal,cta,impressions,likes,reposts,replies,link_clicks,conversions,revenue_yen,ctr,cvr,engagement_rate,epc,rpm,recorded_at}]`, one row per post that has a metrics row. `hook`/`structure`/`appeal`/`cta` come from the post's plan (`null` if the post has no plan). All rate/ratio fields are `null` when their denominator is 0 (never a division error). `ctr`=link_clicks/impressions×100, `cvr`=conversions/link_clicks×100, `engagement_rate`=(likes+reposts+replies)/impressions×100, `epc`=revenue_yen/link_clicks (yen per click), `rpm`=revenue_yen/impressions×1000 (yen per 1000 impressions).
- campaign_performance (案件別の比較, derived, not persisted): `[{campaign_id,campaign_name,impressions,link_clicks,conversions,revenue_yen,post_count,ctr,cvr,epc,rpm}]` — `performance` rows summed per campaign, sorted by `revenue_yen` desc.
- analysis: `[{source_id,engagement_rate,score,buzz_score,pattern,lesson,hook,structure,cta,theme,target,appeals:[string],length}]` sorted descending `buzz_score`. `buzz_score` (see `buzz_score()` in `app/domain.py`) weighs reach against `author_followers`, not raw counts — a smaller account with the same reach multiplier scores higher than a larger one. `hook`/`structure`/`cta`/`theme`/`target`/`appeals`/`length` come from `RuleBasedAnalyzer` (see Content analysis below); all illustrative, mock data labelled.
- summary: `{sources,campaigns,review,approved,published,impressions,likes,reposts,replies,link_clicks,conversions,revenue_yen,ctr,cvr,epc,rpm,recommendation}` percentages 0–100, denominator zero => null.
- tasks (「今日やること」, derived, not persisted): `{sources_pending_plan:[id], approved_campaigns:[id], plans_pending_draft:[id], drafts_pending_publish:[id], posts_pending_metrics:[id]}` — id lists, not counts, so the frontend can both show a count and link straight to the relevant screen.
- audit: `[{id,action,entity_type,entity_id,created_at}]` latest 30, no secrets/body.

## POST endpoints

All return updated complete state except export.

- `/api/collect` `{query?:string}`: fetch sources through the active `SourceProvider` (mock-only for now — see Providers) using the saved `collection_settings`, plus `query` appended as a one-off extra keyword (not persisted). Idempotent (`INSERT OR IGNORE`). No external requests.
- `/api/collection-settings` `{keywords:[string]≤10×≤50chars, genre:string≤50chars, watched_accounts:[string]≤10×≤50chars, period_days:int 1-365}`: replace the saved collection settings used by `/api/collect`.
- `/api/sources` `{text,url,author,likes,reposts,replies,impressions,followers,topic,posted_at}`: manual source; URL HTTPS X/twitter post URL only; integers >=0 (`followers` maps to the response's `author_followers`); `posted_at` required, ISO 8601 UTC (`YYYY-MM-DDTHH:MM:SSZ`).
- `/api/profile` `{name,bio,audience,niche,tone,pillars}`: save full profile.
- `/api/campaigns` `{id?:number,name,network,url,affiliate_url,category,target,appeal_points,reward_conditions,prohibited_expressions:[string]≤20×≤100chars,reward_yen,status,notes}`: add/update. Require HTTPS URLs if nonempty. Status changed to applied records manual application status only. Changes invalidate related drafts' checks/approval. Approved requires affiliate_url, user manually confirms in UI.
- `/api/plans/generate` `{campaign_id:number,source_id?:number|null,angle?:string}`: creates a 投稿企画 (plan). Campaign **must be approved** (409 otherwise). If `source_id` given, `hook`/`structure`/`cta`/`appeal` come from that source's `RuleBasedAnalyzer` output and `match_score` from `CampaignMatcher`; otherwise they're derived by analyzing the campaign's own `appeal_points` text and `match_score` is `null`. Never touches the source's raw text beyond classification.
- `/api/drafts/generate-from-plan` `{plan_id:number, style?:string}`: builds a draft from a plan via `Store.draft_generator` (`DraftGenerator` interface, `RuleBasedDraftGenerator` default). `style` is one of `DRAFT_STYLES` keys (`conclusion_first`/`problem_raising`/`comparison`/`bullet_list`/`short_form`, 400 if invalid); omitted/empty picks a style from the plan's `structure`. Calling this repeatedly with different styles for the same plan is how the UI offers "at least 3 phrasings" — each call makes a new draft row, none overwrite each other. Re-checks the plan's campaign is still approved (409 if not, e.g. status changed after the plan was made). Sets the draft's `plan_id`. Draft still must pass `/api/drafts/check` (PR disclosure, exact URL, prohibited expressions, etc.) before approval.
- `/api/drafts/generate` `{campaign_id?:number|null,source_id?:number|null,angle?:string}`: template-based Japanese draft using profile + optional campaign/source; no LLM. Campaign must be approved to generate promotion. Draft with campaign includes `【PR】`, exact affiliate_url, no invented personal experience or factual benefit. When `source_id` is set, the draft's hook/body/CTA are built from that source's `RuleBasedAnalyzer` **category labels only** (`build_reference_draft()`) — the source's original text is never copied into the generated draft. For sample content set is_mock true. (This path always uses the single `build_reference_draft` template, not the 5 `DRAFT_STYLES` — those are specific to plan-based generation.)
- `/api/drafts/save` `{id?:number,title,text,campaign_id?:number|null,source_id?:number|null}`: create/update draft; always reset status=draft/checks=null. Text up to 5000. Manual UI uses same endpoint. Clears `plan_id` if `campaign_id`/`source_id` change from what the draft's plan referenced (keeps it otherwise, e.g. a pure text edit).
- `/api/drafts/check` `{id:number}`: recompute checks and set review (even if previously approved). Check PR disclosure when campaign linked, campaign approved, exact affiliate URL present, none of the campaign's `prohibited_expressions` present (substring match, error `prohibited_expression`), no guaranteed outcomes/false first-person experience, weighted text <=280, nonempty, sample flag warning; missing campaign with promotional-looking text/URL is error. Source facts/rights and truth need human review warning. Warnings do not block, errors block.
- `/api/drafts/approve` `{id:number,confirmed:true}`: recompute checks, require passed=true; explicit human confirmation, set approved. Approval allowed for sample, export remains sample-labelled.
- `/api/drafts/export` `{id:number}`: only approved or exported, recompute gate; return `{text,filename,is_mock}`; for mock append conspicuous `【サンプル・公開不可】` banner before draft. Real content no append. Set exported, no posting.
- `/api/posts/publish` `{draft_id:number, url:string, posted_at:string}`: records that a draft was **manually** posted on X — this endpoint never posts anything itself. Draft must be `approved`/`exported` (409 otherwise) and must currently pass `/api/drafts/check` (409 with the check error otherwise — catches e.g. a campaign that stopped being approved after the draft was written). `url` reuses the same HTTPS x.com/twitter.com individual-post validator as manual sources (`_url(..., source=True)`), so non-X or malformed URLs are rejected (400). `posted_at` ISO 8601 UTC. Upserts by `draft_id` (calling again for the same draft updates url/posted_at, e.g. to fix a typo) and copies `plan_id`/`campaign_id`/`source_id` from the draft onto the new `posts` row.
- `/api/posts/status` `{id:number, status:string}`: change a post's status among `published`/`stopped`/`removed` (400 for any other value). Purely a local status flag — never deletes or edits the real post on X.
- `/api/metrics` `{post_id:number, impressions,likes,reposts,replies,link_clicks,conversions,revenue_yen}`: cumulative manual totals for a **published post** (400 if `post_id` doesn't exist — no draft/status gate beyond the post existing, since even a stopped/removed post keeps its final numbers). Integers >=0; `conversions<=link_clicks<=impressions` and `likes/reposts/replies<=impressions` (400 otherwise — catches obvious data-entry mistakes; X's own counts are not enforced beyond this). Upserts per `post_id`.

## Providers (`app/domain.py`)

`SourceProvider` is an abstract `fetch(settings) -> [source dict]`. `MockSourceProvider` (the only implementation today) filters the fixed `MOCK_SOURCES` fixture by `keywords`/`genre`/`watched_accounts`; it performs no network I/O. `Store.provider` is `MockSourceProvider()` when `mode == "mock"` and `None` otherwise — `/api/collect` fails closed (503) whenever `provider is None`. A future `XApiSourceProvider` (read-only) can implement the same `fetch(settings)` signature and be wired into `Store.__init__` without changing `_mutate` or the frontend. Initial demo seeding (`Store._initialize`) always uses `MockSourceProvider` directly regardless of `mode`, so constructing a `Store(mode="live")` still succeeds — only the on-demand `/api/collect` call is blocked.

## Content analysis (`app/domain.py`)

`ContentAnalyzer.analyze(text, topic, audience) -> {hook,structure,cta,theme,target,appeals,length}` is the pluggable interface; `RuleBasedAnalyzer` (regex-based, `Store.analyzer` default) is the only implementation today. A future LLM-backed analyzer can implement the same signature and be swapped into `Store.__init__`. Draft generation (`build_reference_draft`) consumes only the returned category labels (e.g. `hook: "question"`) via `HOOK_TEMPLATES`/`STRUCTURE_BODIES`/`CTA_TEMPLATES`, never the source's raw text — this is how "reference this post's structure" avoids copying.

## Matching (`app/domain.py`)

`CampaignMatcher.match(campaign, content, profile) -> {score:0-100, reasons:[string]}` is the pluggable interface; `RuleBasedMatcher` (`Store.matcher` default) is the only implementation today, using a dependency-free character-bigram Jaccard similarity (`_similarity()`) — no external NLP library. Score breakdown (documented in the class docstring so it stays easy to retune): genre match (campaign `category` vs. the post's analyzed `theme`) up to 35, target match (`target` vs. `target`) up to 25, shared appeal categories up to 20, profile fit (`niche`+`pillars` vs. campaign `category`+`target`) up to 20. The post's `structure` is reported in `reasons` for context but is not scored (no campaign-side counterpart exists yet). A future AI-based matcher can implement the same `match()` signature and be swapped into `Store.__init__`.

## Draft generation from a plan (`app/domain.py`)

`DraftGenerator.generate(plan, campaign, profile, style=None) -> str` is the pluggable interface; `RuleBasedDraftGenerator` (`Store.draft_generator` default) is the only implementation. `style` picks one of 5 named styles (`DRAFT_STYLES`) — deliberately distinct structures, not random rewording:

| key | label | shape |
|---|---|---|
| `conclusion_first` | 結論先出し型 | states the conclusion, then the reason |
| `problem_raising` | 問題提起型 | poses a relatable problem/question first |
| `comparison` | 比較型 | lists comparison axes (費用/対象者/条件) |
| `bullet_list` | 箇条書き型 | audience-first checklist |
| `short_form` | 短文型 | minimal, two short lines |

Each style's body is followed by the plan's `CTA_TEMPLATES` line, then a fixed `【PR】`/campaign-name/exact-`affiliate_url` block — that suffix never changes, so whichever style is picked still satisfies `/api/drafts/check`'s PR-disclosure and exact-URL requirements. Omitting `style` maps the plan's `structure` to a sensible default (`_default_style`). A future LLM-backed generator can implement the same signature (including `style` as a hint) and be swapped into `Store.__init__`; the PR-disclosure, exact-URL, and prohibited-expression checks in `/api/drafts/check` still apply regardless of which generator produced the text.

## Publishing via X Web Intent (`app/domain.py`)

`PublishProvider.build_intent_url(text) -> str` is the pluggable interface; `WebIntentPublishProvider` (`Store.publish_provider` default, the only implementation today) is the entire feature: it concatenates X's official compose-intent endpoint (`https://x.com/intent/tweet`) with the draft text as a `text` query parameter, built via `urllib.parse.urlencode` (never raw string concatenation), and returns the URL. That's it — no HTTP request, no OAuth, no session/cookie/token of any kind touches this server. Opening that URL (a plain `<a target="_blank">` in the frontend, not an API call) takes the human to X's own compose screen with the text pre-filled; **only the human's own click on X's "Post" button actually publishes**, and this app has no way to detect that click happened — Web Intent carries no callback, webhook, or completion signal. That is why `publish_intent_url` existing, or even being opened, never changes any status in this app: the human must separately register the resulting post URL via `/api/posts/publish` (unchanged from the previous release — this feature reuses it as-is) before anything becomes `published`. A future paid, authenticated `XApiPublishProvider` (official X API) could implement the same `build_intent_url`-shaped interface (or a richer one, e.g. an actual `publish()` method) and be swapped into `Store.__init__`; **it is not implemented here, and no code toward it (HTTP client, OAuth, API keys) exists in this codebase.**

## Publishing and performance (`app/domain.py`)

The loop this version closes: 探す(research) → 分析する(analysis) → 案件を選ぶ(campaigns + matches) → 企画する(plans) → 文章を作る(drafts, 5 styles) → **自分でXへ投稿**(Web Intent opens X's compose screen; the human reviews and clicks X's own "Post" button) → **記録する**(`/api/posts/publish`) → 数字を入力する(`/api/metrics`) → 勝ちパターンを見つける(`performance`/`campaign_performance`) → 次の投稿に反映する (back to 企画する). Every step after "自分でXへ投稿" is a human typing in what already happened; nothing in this loop calls out to X, an ASP, or an LLM.

`posts` and `metrics` are separate tables so a post's lifecycle (published/stopped/removed) is independent of its draft's editing lifecycle, and so `performance` can be computed per **post** — the unit an actual reward gets attributed to — rather than per draft. `_migrate_pre_create` drops and recreates `metrics` if it finds the pre-`posts`-feature schema (`draft_id` column) on open, since those old rows have no post to attach to; this only affects local databases created before this feature existed. See "既存DBからのマイグレーション" note in ARCHITECTURE.md.

## Frontend

8 nav views: overview/dashboard (①→⑧ flow at a glance, a **今日やること** task list pointing at the next unblocked step, and the daily recommendation), research (①collection settings + manual sources, ②buzz-scored analysis with hook/structure/CTA/appeals + "generate from this structure"), profile (③), campaigns (④ candidate search/filter + form + match candidates with reasons for approved campaigns + "create a plan"), studio (⑤ plans list showing campaign → reference analysis → plan → draft(s), a style picker + "create a draft from this plan" that can be clicked repeatedly for different styles, plus direct template generation + editable drafts), review (⑥ checks + explicit human approval + text export + a link into 投稿管理 once approved), **publish (⑦投稿管理: pending-publish drafts get a prominent "Xで投稿" link when `publish_intent_url` is set — opens X's compose screen in a new tab with the approved text pre-filled, nothing else — plus a "投稿しました" form for the live X URL + posted-at; already-published posts get a "Xで見る" link to the saved URL instead, plus stop/remove/reinstate status controls)**, analytics (⑧cumulative record + per-post performance table with hook/structure/CTA + CTR/CVR/engagement rate/EPC/RPM, plus a per-campaign comparison table). Show mock/local badges and practical empty/loading/error states. Use full state reload after mutation. External services not connected; never expose keys. No auto publishing or actual application UI. Layout should be polished, Japanese, responsive and accessible.
