# 設計

## 方針

このMVPは、運用判断を支えるローカル台帳です。自動投稿や自動申請を初期版から行うと、誤投稿、重複投稿、認証情報の漏えい、案件条件の見落としが起きやすいため、最後の操作は人が行います。

**最初の報酬が発生するまでは、有料API（Claude/OpenAI等のLLM API、X API、ASPのAPI）を一切使わない方針**です。情報収集・分析・案件マッチング・投稿文生成は、すべてルールベース（`RuleBasedAnalyzer`/`RuleBasedMatcher`/`RuleBasedDraftGenerator`）で完結します。将来これらをAPIベースの実装に差し替える設計（下記「差し替え可能な構造」）は維持しますが、実際に差し替えるのは収益化を確認した後の判断です。

```text
ブラウザ（8画面の管理画面）
        ↓ ローカルHTTPのみ
Pythonサーバー（入力検証・検品・承認ゲート）
        ↓
SQLite（プロフィール・参考投稿・案件・投稿企画・下書き・投稿記録・成果）
```

すべてPython標準ライブラリとブラウザ標準機能で構成し、依存パッケージを増やしていません。

## 運用ループ（8つの役割）

「探す → 分析する → 案件を選ぶ → 企画する → 文章を作る → 自分でXへ投稿 → 数字を入力する → 勝ちパターンを見つける → 次の投稿に反映する」という一連のループを、APIコスト0円のまま最初の報酬発生まで回せることを目標にしています。

| 役割 | MVPでの処理 | 人が確認すること |
|---|---|---|
| 情報収集 | キーワード・ジャンル・参考アカウント・期間を設定し、`SourceProvider`（現在は `MockSourceProvider` のみ）経由で架空データを取得。実在の投稿は手入力 | 出典、利用条件、数値、時期 |
| バズ投稿分析 | フォロワー数に対する伸びを表す「バズスコア」、`RuleBasedAnalyzer` によるフック・構成・CTA・訴求パターンのルールベース分類 | 因果関係を断定しない、転載しない |
| プロフィール設計 | 読者・テーマ・文体・発信の柱を保存 | 実際のXプロフィールへの反映 |
| 案件管理 | 候補から停止までの状態・URL・ジャンル・ターゲット・訴求ポイント・報酬条件・禁止表現を保存。提携承認済み案件は `CampaignMatcher` でバズ投稿分析・プロフィールとの0〜100点マッチ度と理由を算出 | ASPで探索・申請・承認を確認 |
| 投稿企画・制作 | マッチ度の高い組み合わせから「投稿企画」（ターゲット/テーマ/フック/構成/訴求/CTA）を作成し、`DraftGenerator` で5スタイル（結論先出し型・問題提起型・比較型・箇条書き型・短文型）から下書きへ。方針と承認案件から直接雛形を作ることも可能 | 事実、価格、条件、独自性 |
| 投稿前検品 | PR表示、正確なURL、案件承認、禁止表現、概算文字数、危険表現 | 法令・規約・案件条件を含む最終判断 |
| **投稿管理** | **承認済み下書きに「Xで投稿」ボタン（X公式Web Intentの投稿作成画面を本文入力済みで開く。自動投稿ではない）。実際にXへ投稿した後の「投稿済み」記録（URL・日時・使用したdraft/plan/campaign/source）。公開中/停止/削除の状態管理** | **Xの画面で最終確認し、「ポストする」は必ず自分で押す。投稿後はXの投稿URLを自分で登録する** |
| 成果分析 | 投稿ごとに表示回数・いいね・リポスト・返信・リンククリック・成果・売上を手入力し、CTR/CVR/エンゲージメント率/EPC/1000impあたり報酬を自動計算。投稿別・案件別に比較し、フック・構成・訴求・CTAごとの傾向を確認 | 同一期間・同一定義の数値を入力、因果関係は断定しない |

## データと境界

`app/domain.py` が入力検証と状態遷移を担当し、`app/server.py` がローカルHTTPとCSRF対策を担当します。認証情報はクライアントやDBへ渡しません。将来のAPI接続は、別のサーバー側アダプターとして追加し、取得元・取得日時・権限・レート制限を保存する設計が適しています。

文字数は安全側の概算です。日本語などを2、URLを最低23として数えます。Xの正式な算定と一致する保証はないため、公開時にXの入力欄でも確認します。

反応スコアは `（いいね + リポスト×2 + 返信×1.5）÷表示回数×100` です。比較の入口であり、成果や再現性を予測する指標ではありません。

バズスコアは、単純な反応数の大小ではなく「フォロワー数に対してどれだけ伸びたか」を見る指標です。`表示回数÷フォロワー数（拡散倍率）×（1＋重み付き反応率）` で計算し、重みは `app/domain.py` の `BUZZ_SCORE_WEIGHTS` にまとめているため、計算式そのものの調整は `buzz_score()` 関数を直接書き換えるだけで完結します。

成果（`metrics`）は下書き（`drafts`）ではなく、実際にXへ投稿した記録（`posts`）に紐付けます。下書きは何度でも編集・再生成できる一方、投稿は一度Xに出したら実体が固定されるため、「どの投稿が実際にいくら生んだか」を後から正確に追えるようにする設計です。CTR/CVR/エンゲージメント率/EPC（1クリックあたり報酬）/1000impあたり報酬は、いずれも分母が0の場合に例外を投げず `null` を返します。

### 既存DBからのマイグレーション

`posts` テーブルは今回新設されたため、旧バージョンの `metrics`（`draft_id` 基準）は新しい `post_id` 基準の設計とかみ合いません。起動時に `Store._migrate_pre_create` が旧スキーマ（`draft_id` 列の有無）を検出した場合、`metrics` テーブルを再作成します（対象は「投稿管理」機能が存在する前に作られたローカルDBのみで、他のテーブル・データは影響を受けません）。旧DBに成果の手入力データが残っていた場合、それらは「どの投稿にも紐付かない」ため保持できず削除されます。これは意図的な設計判断で、本番運用が始まる前の版でのみ発生します。

### 無料版X投稿連携（X Web Intent）

「Xで投稿」ボタンは、X公式の投稿作成画面（`https://x.com/intent/tweet?text=...`）を新しいタブで開くだけです。本文は承認済み下書きの内容をそのまま`text`パラメータに渡します（`urllib.parse.urlencode`で安全にエンコード、文字列連結はしません）。このボタンを押しただけ、あるいはXの画面を開いただけでは、アプリ内のどの状態も変わりません。

**重要な制約**: X Web Intentには投稿完了を知らせる仕組み（コールバック・Webhook等）が一切ないため、**実際にXへ投稿されたかどうかをこのアプリはAPIなしで自動判定できません。** ユーザーがX上で内容を最終確認し、「ポストする」を押すところまでは必ず人が行い、その後アプリに戻って投稿URLを自分で登録して初めて`published`になります（`/api/posts/publish`、既存の投稿管理機能をそのまま再利用）。未承認・検品NGの下書きは`publish_intent_url`がサーバー側で`null`になるため、「Xで投稿」ボタン自体が表示されません（既存の検品を迂回する経路にはなりません）。

- ログイン情報・Cookie・セッション・パスワード・アクセストークンは一切要求・取得・保存しません
- サーバーからXへの通信は発生しません（新しいタブを開くのはブラウザの操作で、CSPの`connect-src`等が制御する範囲には該当しません）
- 既存のCSRF・CSP・Host/Originチェックは変更していません

## 差し替え可能な構造

- **情報収集**: `SourceProvider.fetch(settings)` が抽象化の境界です。`MockSourceProvider` が唯一の実装で、外部通信を一切行いません。将来 `XApiSourceProvider` を追加する場合も同じシグネチャで実装し、`Store.__init__` の生成箇所を差し替えるだけで済むようにしています。実接続の可否は `Store.provider` が `None` かどうかで fail-closed に判定します。
- **投稿内容分析**: `ContentAnalyzer.analyze(text, topic, audience)` が抽象化の境界です。`RuleBasedAnalyzer`（正規表現ベース）が既定実装で、将来 LLM ベースの分析へ差し替える場合も同じ戻り値の形（hook/structure/cta/theme/target/appeals/length）を維持すれば、投稿制作側のコードは変更不要です。
- **参考投稿からの投稿案生成**: `build_reference_draft()` は分析結果の分類ラベル（hook/structure/cta の種類）だけを見てテンプレートを組み立て、原文の文字列は一切参照しません。「構成だけ参考にして転載しない」という要件を、実装レベルで強制しています。
- **案件マッチング**: `CampaignMatcher.match(campaign, content, profile)` が抽象化の境界です。`RuleBasedMatcher`（文字バイグラムの類似度＋訴求パターンの重なり）が既定実装で、内訳（ジャンル35点・ターゲット25点・訴求20点・発信方針20点）はクラスのdocstringにまとめています。将来AI判定へ差し替える場合も同じ `{score, reasons}` の形を維持すれば、案件管理・投稿制作側のコードは変更不要です。
- **投稿企画からの下書き生成**: `DraftGenerator.generate(plan, campaign, profile, style=None)` が抽象化の境界です。`RuleBasedDraftGenerator`（5スタイルのテンプレート組み立て、`DRAFT_STYLES` で一覧管理）が既定実装で、将来LLM Providerへ差し替える場合も同じシグネチャ（`style` をヒントとして渡せる）で実装すれば済みます。どの実装が生成しても、`/api/drafts/check` のPR表示・URL完全一致・禁止表現チェックは必ず通ります。
- **X投稿連携**: `PublishProvider.build_intent_url(text)` が抽象化の境界です。`WebIntentPublishProvider`（Web IntentのURLを組み立てるだけ）が既定実装で、将来 `XApiPublishProvider`（公式X API・有料）へ差し替える場合も `Store.publish_provider` の生成箇所を変えるだけで済みます。ただし今回は`XApiPublishProvider`を実装せず、そこへ向けた通信コードも一切書いていません。

## 次の段階

**最初の報酬が発生するまでは着手しない**（方針を参照）:

1. X APIの読み取り専用アダプター（`XApiSourceProvider`）と取得履歴
2. 投稿内容分析のLLMベース実装への差し替え（`ContentAnalyzer` の新しい実装として追加）
3. 案件マッチングのAI判定への差し替え（`CampaignMatcher` の新しい実装として追加）
4. 下書き生成のLLM Providerへの差し替え（`DraftGenerator` の新しい実装として追加）
5. 公式X APIによる投稿・投稿完了の自動検知（`XApiPublishProvider` の新しい実装として追加）。実装するまでは、投稿の実行・完了確認は引き続き人が行う

**報酬発生の有無に関わらず、無料の範囲で改善できるもの**:

5. 利用するASPごとの規約に合わせた案件取込
6. 実データとサンプルデータをDB単位で分離
7. 集計期間、費用、媒体横断の分析
8. ルールベース分類（フック・構成・訴求・CTA検出）の語彙拡充
9. 投稿は引き続き明示的な承認・人による手動投稿を前提とする
